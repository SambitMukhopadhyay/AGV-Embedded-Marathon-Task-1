# AGV-Embedded-Marathon-Task-1

RTL and testbenches for the **entire** camera-to-VGA pipeline on the DE0-Nano (Cyclone IV E): configuring the OV7670 over SCCB, capturing its pixel stream, storing the captured pixels in a buffer, and displaying them on a VGA monitor. All modules are synchronous Verilog with active-low synchronous resets.

This document covers:

| Module | File | Clock domain | Role |
|---|---|---|---|
| Capture | `captureModule.v` | PCLK (from camera) | Turns the camera's byte stream into 16-bit RGB565 pixels with coordinates |
| SCCB master | `sccbMaster.v` | 50 MHz | Sends one register write to the camera over SCCB |
| Sequencer | `sequencer.v` | 50 MHz | Feeds a table of register writes to the SCCB master and reports when configuration is complete |
| Input top | `inputTopModule.v` | 50 MHz + PCLK | Wires the above together with the reset/enable synchronizers and the clock/reset controller |
| Clock/reset controller | `clockAndResetControl.v` | 50 MHz | Brings up XCLK, releases the camera's power-down and reset in order, raises `cam_ready`, and produces `sys_reset_n` |
| Reset synchronizer | `resetSynchronizer.v` | One instance per clock | Asserts a reset asynchronously and releases it in step with the instance's clock |
| Enable synchronizer | `enSynchronizer.v` | PCLK | Brings `config_done` from the 50 MHz domain into PCLK |
| VGA timing generator | `vgaTimingGenerator.v` | Pixel clock (25 MHz) | Scan counters, HSYNC and VSYNC, the `visible` flag and the read position `x`, `y` |
| Buffer | `buffer.v` | PCLK (write), pixel clock (read) | 160×120 frame store between the camera and the display |
| Output top | `outputTopModule.v` | 50 MHz + pixel clock | Pixel-clock PLL, pixel-domain reset, timing generator and the colour stage |
| Top level | `topModule.v` | All | Connects the input top, the buffer and the output top to the board's pins |

The clock/reset controller, reset and enable synchronizers, buffer and VGA output path are documented separately.

## 1. System context

```
50 MHz ──► clockAndResetControl ──► XCLK, cam_reset_n, pwdn ──► OV7670
                  │
                  ├─ cam_ready ──► sequencer ──► sccbMaster ──► SIOC / SIOD ──► OV7670
                  │                    │
                  │              config_done
                  │                    ▼
                  │             enSynchronizer ──► en_pclk_sync ─┐
                  │                                              │
OV7670 ──► PCLK, VSYNC, HREF, D[7:0] ──► captureModule ◄─────────┘
                                              │
                                              ▼
                       pixel[15:0], pixel_valid, pixel_no[9:0], line_no[8:0]   (PCLK domain, to the buffer)
```

**Clock domains**

| Domain | Source | Modules |
|---|---|---|
| 50 MHz | On-board oscillator | `clockAndResetControl`, `sequencer`, `sccbMaster` |
| PCLK | Generated by the camera from the XCLK the FPGA supplies | `captureModule`, `resetSynchronizer` and `enSynchronizer` instances |

The only signals that cross from the 50 MHz domain into PCLK are the reset (through `resetSynchronizer`) and `config_done` (through `enSynchronizer`). The pixel stream leaves the PCLK domain through the buffer, which is documented separately.

**Start-up order**

1. `clockAndResetControl` brings up XCLK, releases the camera's reset and waits out the camera's power-up time, then raises `cam_ready`.
2. The sequencer starts only when `cam_ready` is high. It writes the soft reset, waits, then writes the remaining registers through the SCCB master.
3. When the last write completes, the sequencer raises `config_done`. After synchronization into the PCLK domain this enables the capture module.
4. The capture module ignores the camera until the next VSYNC rising edge, then emits only complete frames.

**Output half and the third clock domain**

The pixel stream leaves the PCLK domain through the buffer and is displayed from a third clock domain, the 25 MHz pixel clock `clk_pix`, which is generated on chip from the 50 MHz clock.

```
captureModule ──► pixel, pixel_valid, pixel_no, line_no ──► buffer ──► rd_data ──► colour stage ──► colour[15:0] ──► R2R ladders ──► VGA R, G, B
   (PCLK)                                  (write: PCLK)  (read: clk_pix)               ▲
                                                                  ▲                     │ visible
                                                                  │ x, y                │
50 MHz ──► pix_pll ──► clk_pix ──► vgaTimingGenerator ────────────┴─────────────────────┘
                                          │
                                          └──► hsync_n, vsync_n ──► VGA HSYNC, VSYNC
```

| Domain | Source | Modules |
|---|---|---|
| `clk_pix` | `pix_pll` (25 MHz, generated from the 50 MHz clock) | `vgaTimingGenerator`, the buffer's read side, the pixel-domain `resetSynchronizer` instance, the colour stage |

Every crossing between the three domains goes through one dedicated mechanism:

| Crossing | Mechanism |
|---|---|
| Reset button → each domain | `resetSynchronizer`, one instance per domain |
| `config_done` → PCLK | `enSynchronizer` |
| Pixel data, PCLK → `clk_pix` | The buffer's dual-clock RAM |
| PLL `locked` → 50 MHz | Two-flop synchronizer inside `clockAndResetControl` |
| PLL `locked` → `clk_pix` | Raw input of the pixel-domain `resetSynchronizer` |

**Reset distribution**

| Reset | Clock | Raw input | Used by |
|---|---|---|---|
| 50 MHz synchronized reset | 50 MHz | Reset button | `clockAndResetControl` |
| `sys_reset_n` | 50 MHz | Made by `clockAndResetControl`; stays low until the camera PLL has locked | `sequencer`, `sccbMaster` |
| `reset_pclk_sync_n` | PCLK | `sys_reset_n` | `enSynchronizer`, `captureModule` |
| `reset_pix_sync_n` | `clk_pix` | Reset button AND the `pix_pll` lock | `vgaTimingGenerator` |

A module's reset is always synchronized to the clock that module runs on. The buffer has no reset: a RAM does not need one, and every location holds stale or undefined data until the camera has written it.

## 2. `captureModule`

### Function

Runs entirely on the camera's PCLK. On each rising PCLK edge while HREF is high, it takes one byte from `D[7:0]`. Two consecutive bytes (high byte first, RGB565) form one 16-bit pixel. It also tracks the pixel's position in the frame and flags the start of each frame.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `pclk` | in | 1 | Pixel clock from the camera |
| `vsync` | in | 1 | Frame marker from the camera (rising edge = new frame) |
| `href` | in | 1 | High while `d` carries valid pixel bytes of a line |
| `d` | in | 8 | Pixel data byte |
| `en_sync` | in | 1 | Enable, already synchronized to PCLK (driven by `config_done`) |
| `reset_sync_n` | in | 1 | Active-low reset, already synchronized to PCLK |
| `pixel` | out | 16 | Assembled RGB565 pixel |
| `pixel_valid` | out | 1 | One-cycle pulse: `pixel` is valid in this cycle |
| `frame_start_flag` | out | 1 | One-cycle pulse at the start of each captured frame |
| `pixel_no` | out | 10 | Index of the current pixel within its line (0-based) |
| `line_no` | out | 9 | Index of the current line within the frame (0-based) |

### Behaviour

- **Byte pairing.** A flag (`high_byte`) alternates between "next byte is the high half" and "next byte is the low half". The low byte completes the pixel and raises `pixel_valid` for one cycle.
- **Edge detection.** VSYNC rising and HREF falling are detected by comparing each signal with a one-cycle-delayed copy (`vsync_d`, `href_d`). VSYNC and HREF are treated as data, never as clocks, so the module has one clock domain and every register has one driver.
- **Line and frame boundaries.** HREF falling ends a line (`pixel_no` returns to 0, `line_no` increments, byte pairing re-aligns). VSYNC rising starts a frame (`line_no` and `pixel_no` return to 0, byte pairing re-aligns, `frame_start_flag` pulses).
- **Clean start.** While `en_sync` is low (or in reset), the module is held idle. After `en_sync` goes high it still waits for the first VSYNC rising edge before capturing, so the first output frame is always complete and never a partial one.

### Design notes

- **Coordinates are aligned with the data.** `pixel_no` increments on the cycle after `pixel_valid`, so while `pixel_valid` is high it holds that pixel's own 0-based index. Downstream logic can use `(pixel_no, line_no)` directly as the write position, with no off-by-one correction.
- **End-of-line precedence.** The HREF-falling reset of `pixel_no` is written after the increment, so for the last pixel of a line the reset wins and the next line starts at 0.
- **Reset covers control state only.** Counters, flags and strobes are reset. The `pixel` data register is not, because it is always written before `pixel_valid` marks it as meaningful. The delayed copies `vsync_d` and `href_d` sit outside the reset branch so they keep tracking the inputs even while the module is idle.
- **Source-synchronous capture.** Sampling uses the camera's own PCLK, which travels with the data, not the XCLK the FPGA supplies. This avoids depending on the camera's internal delay.

### Assumptions

- Output format is RGB565 with the high byte first (configured through SCCB).
- HREF stays low during vertical blanking, so `line_no` counts only real lines. After the last line of a 480-line frame it reads 480.
- `reset_sync_n` and `en_sync` are already synchronous to PCLK (provided by the top-level synchronizers).
- The module has no knowledge of image size; it reports positions and leaves interpretation to the next stage.

## 3. `sccbMaster`

### Function

A write-only SCCB master. When asked, it sends one 3-byte register write to the camera — device address, register address, data — and reports completion. It knows nothing about which registers to write or in what order.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_50MHz` | in | 1 | Board clock (the only clock in this module) |
| `reset_n` | in | 1 | Active-low synchronous reset |
| `start` | in | 1 | One-cycle request to send a write |
| `reg_addr` | in | 8 | Camera register address |
| `reg_data` | in | 8 | Value to write |
| `busy` | out | 1 | High while a write is in progress |
| `done` | out | 1 | One-cycle pulse when a write has finished |
| `sioc` | out | 1 | SCCB clock (registered output) |
| `siod` | inout | 1 | SCCB data (driven or released) |

### Frame format

One write sends 27 bits, most significant bit first:

| Byte | Contents | Followed by |
|---|---|---|
| 1 | `0x42` (device address, write) | ACK slot (released) |
| 2 | `reg_addr` | ACK slot (released) |
| 3 | `reg_data` | ACK slot (released) |

preceded by a start marker and followed by a stop marker.

### Timing scheme

The module stays on the 50 MHz clock. A counter produces a one-cycle **tick every 125 cycles (2.5 µs)**, and the FSM advances only on ticks. Each SCCB bit takes four ticks (10 µs, i.e. a 100 kHz SCCB clock):

| Slot | SIOC | SIOD |
|---|---|---|
| 1 | low | changes to the new bit |
| 2 | rises | held |
| 3 | high | held (the camera samples here) |
| 4 | falls | held |

SIOD therefore changes only while SIOC is low and well away from either SIOC edge.

**Start marker** (3 ticks): SIOC and SIOD high → SIOD falls while SIOC is high → SIOC falls.
**Stop marker** (3 ticks): SIOC rises while SIOD is low → SIOD rises while SIOC is high.

Each of these changes happens in its own tick, which is what guarantees the ordering that the protocol requires.

A complete write takes 114 ticks, about **285 µs**.

### FSM states

| State | Action |
|---|---|
| S0 | Idle level: SIOC and SIOD high |
| S1 | Start marker: SIOD falls (SIOC still high) |
| S2 | Start marker: SIOC falls |
| S3 | Bit slot 1: drive the next bit on SIOD (or release SIOD in an ACK slot) |
| S4 | Bit slot 2: SIOC rises |
| S5 | Bit slot 3: hold |
| S6 | Bit slot 4: SIOC falls; advance bit index; go to S3, or to S7 after the last bit |
| S7 | Stop marker: SIOC rises |
| S8 | Stop marker: SIOD rises |
| S9 | Finish: `busy` falls and `done` pulses |

### Design notes

- **No derived clock.** The 100 kHz timing comes from a clock-enable tick, not a divided clock, so there is a single clock domain and no crossing between the master and the logic that controls it. SIOC is simply a registered output that the FSM drives.
- **Bit order.** The 27-bit vector `{0x42, X, reg_addr, X, reg_data, X}` is read from bit 26 down to bit 0 by a descending index. The three placeholder positions (indices 18, 9 and 0) are the ACK slots.
- **ACK handling.** In the ACK slots SIOD is released (high impedance, through the `ignore_bit` enable), and the master does not depend on the camera's answer, following the SCCB "don't care" 9th bit.
- **Tri-state.** SIOD is driven by `assign siod = ignore_bit ? 1'bz : siod_temp`, so the register that holds the bit value always contains a plain 0 or 1.
- **Handshake.** `start` is accepted outside the tick gating, so a one-cycle pulse is never missed. On the accepting edge, `busy` rises and `reg_addr` and `reg_data` are latched, so the caller can change them during the write. A `start` that arrives while `busy` is high is ignored. `busy` falls on the same edge that `done` pulses.
- **Idle level.** SIOC and SIOD both idle high between writes.

### Notes

- Only writes are implemented. Reads are not needed for configuration.
- The SCCB bus needs a pull-up on SIOD (many OV7670 breakout boards include one); simulation uses `pullup(siod)`.

## 4. `sequencer`

### Function

Holds the camera's configuration as a table of (register address, value) pairs and feeds it, one entry at a time, to the SCCB master. Raises `config_done` when every entry has been sent. It knows nothing about SCCB bit timing.

### Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `TOTAL_ENTRIES` | 3 | Number of entries in the table |
| `WAIT_COUNT` | 500000 | Clock cycles to wait after the soft reset (10 ms at 50 MHz) |

Counter widths are derived with `$clog2`, so both parameters can be overridden (for example, to a small value in simulation).

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_50MHz` | in | 1 | Board clock |
| `reset_n` | in | 1 | Active-low synchronous reset |
| `cam_ready` | in | 1 | From the clock/reset controller: camera power-up wait finished. Nothing starts before this |
| `sccb_busy` | in | 1 | From the SCCB master |
| `sccb_done` | in | 1 | From the SCCB master (one-cycle pulse) |
| `reg_addr` | out | 8 | Register address of the entry being sent |
| `reg_data` | out | 8 | Value of the entry being sent |
| `start` | out | 1 | One-cycle pulse: send this entry now |
| `config_done` | out | 1 | High once all entries have been sent (held until reset) |

### Table

The table is a combinational `case` on the entry index that returns one 16-bit word `{address, data}`. Entry 0 must be the soft reset (COM7 `0x12` ← `0x80`). A `default` branch returns `16'hFFFF`, so every path assigns the output. Adding or changing a register means editing one line.

> **Status:** entries after the soft reset are currently placeholders; the final register list is taken from the OV7670 datasheet and implementation guide.

### FSM states

| State | Action | Moves on when |
|---|---|---|
| S0 | Send entry 0 (soft reset): load the table word, pulse `start` | Immediately → S1 |
| S1 | Post-reset wait: count `WAIT_COUNT` cycles | Counter expires → S2 |
| S2 | If the SCCB master is not busy, load the next entry and pulse `start` | Next cycle → S3 |
| S3 | Wait for `sccb_done` | `sccb_done` pulses: all entries sent → S4, otherwise → S2 |
| S4 | `config_done` held high | Never (until reset) |

### Design notes

- **Waits for `done`, not `busy`.** `busy` rises one cycle after `start`, so a wait based on `busy` falling could end immediately. Waiting for the one-cycle `sccb_done` pulse avoids this, and also guarantees that `config_done` rises only after the last write has finished on the bus.
- **Soft-reset wait.** Writes sent to the camera too soon after the soft reset are lost, so the sequencer waits `WAIT_COUNT` cycles after entry 0 before sending anything else.
- **Start gating.** `start` is a one-cycle pulse, issued only when `sccb_busy` is low.
- **Steady data.** The table index is held between `start` and `done`, so `reg_addr` and `reg_data` stay constant during each write.
- **Held in reset until the camera is ready.** The module is in reset while `cam_ready` is low, so the sequence starts from entry 0 whenever the camera is brought up. Reset also clears `config_done`.
- **End of table.** Completion is determined by `TOTAL_ENTRIES`, not by a magic table value.

## 4A. `clockAndResetControl`

### Function

Brings the camera up in the order it needs and tells the rest of the design when it is safe to talk to it. It owns the camera clock (XCLK, from an on-chip PLL), keeps the camera in power-down and reset until the PLL has locked, releases them one after the other, waits out the camera's power-up time, and then raises `cam_ready`. It also produces `sys_reset_n`, the reset used by the other 50 MHz modules.

### Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `WAIT_CYCLES_AFTER_PWDN` | 1000 | Clock cycles between releasing power-down and releasing the camera reset (20 µs at 50 MHz) |
| `WAIT_CYCLES_AFTER_RESET` | 500000 | Clock cycles between releasing the camera reset and raising `cam_ready` (10 ms at 50 MHz) |

Counter widths are derived with `$clog2`. Both parameters must be at least 2 if overridden, because `$clog2(1)` is 0 and gives an invalid range.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_50MHz` | in | 1 | Board clock, also the PLL reference |
| `reset_n` | in | 1 | Active-low reset, already synchronous to the 50 MHz clock |
| `xclk` | out | 1 | 24 MHz clock supplied to the camera (PLL output) |
| `cam_reset_n` | out | 1 | Camera reset, active low |
| `pwdn` | out | 1 | Camera power-down, active high |
| `cam_ready` | out | 1 | High once the camera's power-up wait has finished |
| `sys_reset_n` | out | 1 | Active-low reset for the other 50 MHz modules |

### PLL

`cam_pll` is an ALTPLL generated in Quartus (50 MHz in, `c0` = 24 MHz as ×12 / ÷25, `locked` output enabled, `areset` input not created) and is instantiated inside this module. Without `areset` the PLL resets itself at power-up, and any later loss of lock is handled by the FSM. The generated files are kept under `ip/`.

### Sequence

Order of events at the pins, from power-up or from the end of a reset:

1. Everything held: `pwdn` high, `cam_reset_n` low, `sys_reset_n` low, `cam_ready` low.
2. The PLL locks (seen through the synchronizer): `pwdn` falls and `sys_reset_n` rises.
3. `WAIT_CYCLES_AFTER_PWDN` + 1 cycles later: `cam_reset_n` rises.
4. `WAIT_CYCLES_AFTER_RESET` + 1 cycles later: `cam_ready` rises and stays high.
5. If `reset_n` goes low or the lock is lost at any point, everything returns to step 1.

The extra cycle in each gap is the state that performs the release.

### FSM states

| State | Action | Moves on when |
|---|---|---|
| S0 | Release power-down (`pwdn` low), raise `sys_reset_n`, clear the PWDN counter | Immediately → S1 |
| S1 | Count `WAIT_CYCLES_AFTER_PWDN` cycles | Counter expires → S2 |
| S2 | Release the camera reset (`cam_reset_n` high), clear the reset counter | Next cycle → S3 |
| S3 | Count `WAIT_CYCLES_AFTER_RESET` cycles | Counter expires → S4 |
| S4 | `cam_ready` held high | Never (until reset or loss of lock) |

While `reset_n` is low or the synchronized lock is low, the module forces `pwdn` = 1, `cam_reset_n` = 0, `cam_ready` = 0 and `sys_reset_n` = 0, clears both counters and sits in S0.

### Design notes

- **Power-down is held until the PLL has locked.** With PWDN low the camera takes XCLK and starts generating PCLK even while its reset is asserted. Keeping PWDN high until lock means the camera never sees an unstable clock. Power-down plus reset is also the safe state, so it is what every output returns to on reset.
- **The lock is synchronized.** `locked` comes from the PLL's internal lock detector and can change at any moment relative to the 50 MHz clock, so it passes through two flops (`lock_meta`, `lock_sync`) and the FSM only looks at `lock_sync`. The reset of these two flops depends on `reset_n` only; tying it to the lock itself would hold them in reset for ever (see section 7).
- **Loss of lock restarts the sequence.** A dropped lock pulls every output back to its reset level, so the camera is power-cycled and re-timed, and the sequencer (held in reset through `sys_reset_n`) starts again from entry 0.
- **One reset test for all states.** The combined reset/lock condition is tested once, outside the `case`, so the individual states do not repeat it.
- **`reset_n` versus `sys_reset_n`.** `reset_n` is only the request to restart. `sys_reset_n` is the module's decision that the hardware underneath is ready, so the rest of the 50 MHz logic never runs while the PLL is still settling. It is a registered output, not a combination of two signals, so it cannot glitch on its way to the flops of other modules. It rises with the PWDN release, long before `cam_ready`; the sequencer is held back by `cam_ready`, not by `sys_reset_n`.
- **Waits are counters.** Each counter is cleared on entering its wait and compared against N−1, so a wait lasts exactly N cycles. Both limits are parameters so the testbench can shorten them.

## 4B. `resetSynchronizer`

### Function

Takes an asynchronous active-low reset and produces a reset that **asserts immediately** and **releases in step with a chosen clock**. It is written once and instantiated once per clock domain.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk` | in | 1 | Clock of the domain being reset |
| `reset_async_n` | in | 1 | Raw active-low reset, not related to `clk` |
| `reset_sync_n` | out | 1 | Active-low reset, released on a `clk` edge |

### Behaviour

Two flops (`reset_meta_n`, `reset_sync_n`) in one block with the sensitivity list `posedge clk, negedge reset_async_n`.

- **Press:** the moment `reset_async_n` falls, both flops clear and `reset_sync_n` goes low, with no clock edge needed.
- **Release:** once `reset_async_n` is high, a constant 1 shifts through the two flops, so `reset_sync_n` rises two `clk` edges later, aligned to that clock.

### Instances

| Clock | Raw reset input | Serves |
|---|---|---|
| 50 MHz | Reset button | `clockAndResetControl` |
| PCLK | `sys_reset_n` | `enSynchronizer`, `captureModule` |
| `clk_pix` | Reset button AND `pix_pll` lock | `vgaTimingGenerator` |

### Design notes

- **The only asynchronous reset in the design.** Every other module uses a synchronous reset. The assert is asynchronous because it then works with no running clock (PCLK comes from the camera and may not run while the camera is held in reset) and cannot miss a press shorter than one clock. The release is the dangerous moment, because flops that see the reset disappear on different edges wake up half-started; synchronizing the release makes every flop in the domain leave reset on the same edge.
- **The first flop's data input is the constant 1.** Inside the release branch the raw reset is always 1 anyway, but a constant keeps the raw reset connected to the flops' asynchronous-clear pins only and out of the data path.
- **The pixel domain needs no separate lock synchronizer.** Its raw input is the button ANDed with the PLL's `locked`. The synchronizer already accepts an asynchronous input, so the pixel side stays in reset until the PLL has locked and `locked` appears in this one place only.
- **Release needs a running clock.** The PCLK instance releases only once PCLK toggles, which is harmless because capture has nothing to do before the camera is configured.
- **The edge in the sensitivity list must match the test.** `negedge reset_async_n` goes with `if (reset_async_n == 1'b0)`, with the reset case first and the shifting in the `else`, which is the form the synthesizer maps onto the flops' clear pins.

## 4C. `enSynchronizer`

### Function

Brings `config_done`, which is produced in the 50 MHz domain, into the PCLK domain as `en_sync`, the enable for `captureModule`.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `pclk` | in | 1 | Receiving clock |
| `config_done` | in | 1 | From the sequencer (50 MHz domain) |
| `reset_sync_n` | in | 1 | Active-low reset, already synchronized to PCLK |
| `en_sync` | out | 1 | `config_done` seen from PCLK |

### Behaviour

Two flops in a row (`en_meta`, `en_sync`) on PCLK. While `reset_sync_n` is low both are 0; otherwise `en_meta` takes `config_done` and `en_sync` takes `en_meta`. `en_sync` therefore follows `config_done`, rising or falling, two PCLK edges later.

### Design notes

- **Only the receiving clock appears.** The 50 MHz clock is not used in this module. `config_done` can change at any moment relative to a PCLK edge; the first flop may go metastable, and the second only ever sees the value it settled on.
- **It relies on `config_done` being a level.** The sequencer raises it once and holds it until reset, so seeing it a couple of cycles late is harmless. The same circuit would not be safe for a one-cycle pulse, which could fall between two PCLK edges and be missed.
- **Reset gives a defined output.** With the reset, `en_sync` is 0 from the first PCLK edge, and capture never sees an undefined enable.
- **The delay costs nothing.** Two PCLK cycles are negligible next to a frame, and capture additionally waits for the next VSYNC.

## 5. `inputTopModule`

Instantiates and connects the modules above with the controller and synchronizers.

**Instances**

| Instance | Module | Clock | Role |
|---|---|---|---|
| `rS` | `resetSynchronizer` | PCLK | Reset asserts asynchronously and releases on a PCLK edge → `reset_pclk_sync_n` |
| `eS` | `enSynchronizer` | PCLK | Two-flop synchronizer bringing `config_done` into PCLK → `en_pclk_sync` |
| `cM` | `captureModule` | PCLK | Pixel capture |
| `sM` | `sccbMaster` | 50 MHz | SCCB writes |
| `s` | `sequencer` | 50 MHz | Configuration table |
| `cARC` | `clockAndResetControl` | 50 MHz | XCLK, camera reset/power-down, `cam_ready`, `sys_reset_n` |

**External ports**

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_50MHz` | in | 1 | Board clock |
| `reset_50Mz_sync_n` | in | 1 | Active-low reset, synchronous to the 50 MHz clock |
| `pclk`, `vsync`, `href` | in | 1 each | Camera pixel clock and sync signals |
| `d` | in | 8 | Camera pixel data |
| `sioc` | out | 1 | SCCB clock to the camera |
| `siod` | inout | 1 | SCCB data |
| `xclk` | out | 1 | Clock supplied to the camera |
| `cam_reset_n`, `pwdn` | out | 1 each | Camera reset and power-down |
| `pixel` | out | 16 | RGB565 pixel (PCLK domain) |
| `pixel_valid` | out | 1 | Pixel valid strobe (PCLK domain) |
| `pixel_no` | out | 10 | Pixel index within the line |
| `line_no` | out | 9 | Line index within the frame |

**Reset distribution.** The 50 MHz modules (`sequencer`, `sccbMaster`) use `sys_reset_n` from the clock/reset controller, which stays low until the camera PLL has locked. The PCLK modules use the synchronized reset `reset_pclk_sync_n`.

**Enable path.** `config_done` is synchronized by `eS` before it reaches `captureModule`'s `en_sync` input.

**Note on the final integration.** In the final top-level wiring the 50 MHz reset synchronizer is instantiated inside this module as well: the external reset port is the raw button (`reset_async_n`), a `resetSynchronizer` on `clk_50MHz` produces the synchronous reset for `clockAndResetControl`, and the PCLK `resetSynchronizer` takes `sys_reset_n` as its raw input, so the capture side is also reset when the camera PLL loses lock. The instances in this version are `clk_50MHz_sync` and `pclk_sync`, and `reset_50Mz_sync_n` in the port table above is replaced by `reset_async_n`.

## 5A. `vgaTimingGenerator`

### Function

A VGA monitor has no memory: it scans line by line, left to right and top to bottom, about 60 times a second, and uses HSYNC to end a line and VSYNC to end a frame. This module is the metronome for that scan. It counts the scan position, produces the two sync pulses and a `visible` flag, and reports the position `x`, `y` so the buffer knows which pixel to read. It never touches colours.

### Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `PIXELS` | 640 | Visible pixels per line |
| `HFPORCH`, `HS`, `HBPORCH` | 16, 96, 48 | Horizontal front porch, sync width, back porch (pixel clocks) |
| `LINES` | 480 | Visible lines per frame |
| `VFPORCH`, `VS`, `VBPORCH` | 10, 2, 33 | Vertical front porch, sync width, back porch (lines) |

The totals (800 clocks per line, 525 lines per frame) are derived from these, and so are the counter widths.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_pix` | in | 1 | Pixel clock (25 MHz) |
| `reset_n` | in | 1 | Active-low reset, already synchronous to `clk_pix` |
| `hsync_n` | out | 1 | Horizontal sync, active low (registered) |
| `vsync_n` | out | 1 | Vertical sync, active low (registered) |
| `visible` | out | 1 | High while the position is inside the 640×480 picture (registered) |
| `x` | out | `$clog2(line total)` | Horizontal position, 0 to 799 |
| `y` | out | `$clog2(frame total)` | Line position, 0 to 524 |

### Timing (640×480 at 60 Hz)

| | Visible | Front porch | Sync | Back porch | Total |
|---|---|---|---|---|---|
| Horizontal (pixel clocks) | 640 | 16 | 96 | 48 | 800 |
| Vertical (lines) | 480 | 10 | 2 | 33 | 525 |

A line takes 32 µs and a frame 16.8 ms at a 25 MHz pixel clock. Every line, including the vertical blanking lines, is 800 clocks long and HSYNC keeps pulsing throughout. During the porches and sync, the colour output is black.

### Behaviour

- **Counters.** `x` adds 1 each clock and wraps from 799 to 0. `y` adds 1 only on the edge where `x` wraps, and wraps from 524 to 0 on that same edge.
- **HSYNC.** Low while `x` shows 656 to 751 (96 clocks), high otherwise.
- **VSYNC.** Low during lines 490 and 491, high otherwise.
- **`visible`.** High while `x` < 640 and `y` < 480.
- **Reset.** Counters to 0, both syncs high (idle), `visible` low.

### Design notes

- **Every output is registered.** The syncs are set from comparisons on the counters inside the one clocked block, so the pins see no glitches. As a result `hsync_n`, `vsync_n` and `visible` appear one clock after the counter values that produced them, which is the same one-clock latency as the buffer's read (see section 5B). The colour and `visible` therefore reach the colour stage together.
- **Boundaries are named.** Every comparison is built from `localparam` names derived from the porch parameters; the only literal-like values are the wrap points (total − 1).
- **HSYNC is lined up with `x`, not with `visible`.** The horizontal comparison is written one count early (655 to 750) so that, after registering, the pulse is low while `x` shows 656 to 751. This puts HSYNC one clock ahead of `visible` and the colour path, so at the pins the front porch is 15 clocks and the back porch 49, with the sync width and the visible width unchanged. Monitors tolerate a one-pixel porch shift; the picture is simply one pixel to the right. The same shift would be a whole line for `y`, which changes only once per line, so the vertical range is written as exactly lines 490 and 491.
- **Counter widths come from the totals.** Sizing from the visible size would overflow `y` (524 does not fit in 9 bits).
- **Pixel clock.** 25.000 MHz is slightly below the nominal 25.175 MHz and gives a frame rate of about 59.5 Hz, which monitors accept.
- **`x` and `y` are meaningful to the buffer only while `visible` is high.** In blanking they keep counting to the totals.

## 5B. `buffer`

### Function

The shared whiteboard between the camera and the display. The camera side writes pixels into a frame store on PCLK, and the display side reads whatever is stored on the pixel clock, 60 times a second, independently of when the camera writes. It is a frame store, not a queue: a pixel is kept until the camera overwrites it.

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `pclk` | in | 1 | Write clock (the camera's PCLK) |
| `pixel` | in | 16 | RGB565 pixel from `captureModule` |
| `pixel_valid` | in | 1 | The pixel is real |
| `pixel_no` | in | 10 | Column of the pixel, 0 to 639 |
| `line_no` | in | 9 | Line of the pixel, 0 to 479 |
| `clk_pix` | in | 1 | Read clock (pixel clock) |
| `x`, `y` | in | 10 each | Scan position from `vgaTimingGenerator` |
| `rd_data` | out | 16 | Stored pixel for the position `x`, `y`, one clock later |

### Sizing

A full 640×480 frame at 16 bits is about 4.9 Mbit, far more than the device's roughly 594 Kbit of on-chip RAM (66 M9K blocks). The buffer therefore stores a **160×120** frame (19,200 words × 16 bits = 307,200 bits) and the display scales it up 4× in each direction.

### Behaviour

- **Write.** A pixel is written only when `pixel_valid` is high and the two lowest bits of both `pixel_no` and `line_no` are `00`, i.e. every 4th pixel of every 4th line. Its address is `(pixel_no >> 2) + 160 × (line_no >> 2)`, from 0 to 19,199.
- **Read.** The address is `(x >> 2) + 160 × (y >> 2)` and `rd_data` is a registered output, so the colour arrives exactly one clock after `x` and `y`. Each stored pixel is therefore shown as a 4×4 block of display pixels.
- **Memory.** One array, written from one block on `pclk` and read from one block on `clk_pix`. This is the pattern the synthesizer maps onto a true dual-clock block RAM, which handles the clock crossing; there is no hand-built FIFO.

### Design notes

- **Everything on the write side is combinational from capture's registers.** The write enable, the address and `pixel` all describe the same pixel in the same cycle, which works because `captureModule` keeps `pixel_no` equal to the pixel's own index while `pixel_valid` is high. No intermediate registers are added, since each one would shift the enable, the address or the colour by a cycle relative to the others.
- **`pixel_valid` gates the write.** `pixel_no` and `line_no` hold their values between pixels, so the low-bits test alone would keep writing garbage to the last address.
- **The read is a single clock.** The address is a wire from `x` and `y`, and the only register on the path is the RAM's read register. That is what keeps the colour aligned with the registered `visible` from the timing generator.
- **No reset, no blanking value.** During blanking `y` runs to 524, so the read address passes 19,199 and reads past the end of the array. This is harmless because the colour stage forces black while `visible` is low (simulation may show X there).
- **Sizes are named.** `ROWS`, `COLS` and the address width are `localparam`s, not parameters: the shifts and the low-bit test are the 4× scale written as bit operations, so the module is correct only for a 640×480 input and a 160×120 store, and a size parameter would suggest otherwise.
- **Tearing.** Read-during-write on a dual-clock RAM is undefined, and the camera (about 30 fps) and the display (about 60 Hz) are not synchronized, so a displayed frame can contain a part of the previous one. This is accepted.

### Assumptions

- `captureModule` delivers 640×480 pixels per frame with 0-based `pixel_no` and `line_no`.
- Quartus infers block RAM from the array (the compile reports 307,200 memory bits).

## 5C. `outputTopModule`

### Function

The VGA side of the design: it makes the pixel clock, holds the display logic in reset until that clock is usable, runs the timing generator and applies the colour stage. The buffer sits outside this module, in `topModule`, because it has a PCLK side as well.

### Instances

| Instance | Module | Clock | Role |
|---|---|---|---|
| `pll2` | `pix_pll` | 50 MHz in | ALTPLL: 25 MHz `c0`, `locked` output, no `areset` |
| `pix_sync` | `resetSynchronizer` | `clk_pix` | Pixel-domain reset; raw input is the button ANDed with the PLL's `locked` |
| `vgaTG` | `vgaTimingGenerator` | `clk_pix` | Scan counters, syncs, `visible`, `x`, `y` |

### Ports

| Port | Dir | Width | Description |
|---|---|---|---|
| `clk_50MHz` | in | 1 | Board clock (PLL reference) |
| `reset_async_n` | in | 1 | Raw active-low reset button |
| `rd_data` | in | 16 | Stored pixel from the buffer |
| `clk_pix` | out | 1 | Pixel clock, for the buffer's read side |
| `x`, `y` | out | 10 each | Scan position, to the buffer |
| `hsync_n`, `vsync_n` | out | 1 each | Sync signals to the monitor |
| `colour` | out | 16 | RGB565 colour after the colour stage (`[15:11]` red, `[10:5]` green, `[4:0]` blue) |

### Colour stage

`colour = visible ? rd_data : 16'h0000`. While `visible` is high the buffer's pixel goes out, and during the porches and sync everything is black, which is what a monitor expects there (it also uses that time to set its black level). The 16 bits then go to the resistor ladders, five for red, six for green and five for blue.

### Design notes

- **The pixel side waits for the PLL.** The raw reset into `pix_sync` is `reset_async_n & lock`, so the timing generator stays in reset until the PLL has locked, and the user does not have to hold the button. Asserting needs no clock, which is why this works while the pixel clock is still unusable; only the release needs it, and by then the clock is running.
- **`lock` appears in one place.** It is not synchronized again in this module, because `resetSynchronizer` already takes an asynchronous input. A second synchronizer in front of it would protect the same crossing twice, and would be on the wrong clock if built on 50 MHz.
- **No extra delay is needed on the syncs.** `visible` and `rd_data` are both one clock after `x` and `y`, so the mux sees them from the same moment. If the colour were registered for cleaner pins, `hsync_n` and `vsync_n` would need one more flop each to stay in line.
- **The colour stage is combinational.** It can show short glitches on the ladder pins when `visible` changes, which a monitor does not notice at this speed.

### Function

The outside of the design. It contains no logic of its own: it holds the input top, the buffer and the output top and connects them to the board's pins.

|---|---|---|

### Connections

| From | To |
|---|---|
| `pclk` pin | `iTM` and the buffer's write clock |
| `iTM`: `pixel`, `pixel_valid`, `pixel_no`, `line_no` | Buffer write side |
| `oTM`: `clk_pix`, `x`, `y` | Buffer read side |
| Buffer `rd_data` | `oTM` |
| `clk_50MHz` and `reset_async_n` | `iTM` and `oTM` |

### Design notes

- **Three clocks, kept apart.** `clk_50MHz`, `pclk` and `clk_pix` all appear here. Each wire goes only to modules that run on that clock, and the buffer is the only module that sees two of them (`pclk` on its write side, `clk_pix` on its read side).
- **Each PLL lives in the module that uses its clock.** `cam_pll` is inside `clockAndResetControl` and `pix_pll` inside `outputTopModule`, so the top level has only pins and wiring and no clock needs to be passed through it.
- **Two different VSYNC signals.** `vsync` is the camera's frame marker coming in; `vsync_n` is the monitor's sync going out. They are unrelated.
- **The PLLs are merged by the Fitter.** The compile reports one physical PLL (`PLL_1`, VCO 600 MHz from the 50 MHz input, M = 12, N = 1) for the two PLL instances. Both requested clocks (24 MHz and 25 MHz) divide exactly from a 600 MHz VCO, so both can be taken from one PLL's output counters. Each module still receives its own clock.

## 6. Verification

Self-checking Verilog testbenches (they print `RESULT: PASS` or `RESULT: FAIL`); simulated with iverilog and ModelSim-compatible constructs.

### `captureModule` testbench

- Camera model drives `pclk`, `vsync`, `href` and `d` on the falling PCLK edge, so the module samples stable data.
- Shrunk frame (4 pixels × 3 lines) with predictable data so every pixel can be identified.
- Two consecutive frames are sent after reset and enable.
- A checker compares each `pixel` against an expected array, and `pixel_no` and `line_no` against the expected coordinates, whenever `pixel_valid` is high.
- Final checks: total valid pixels (24), `frame_start_flag` count (2) and zero errors.

### `sccbMaster` testbench

- A camera-side monitor decodes the bus the way the camera would: START (SIOD falls while SIOC is high), each bit sampled on SIOC rising, STOP (SIOD rises while SIOC is high).
- `pullup(siod)` stands in for the bus pull-up, so a released ACK slot must read 1. A master that kept driving would be caught.
- Three writes: a plain write, a write during which `reg_addr`, `reg_data` and a second `start` are disturbed (the original values must still be sent and the extra `start` ignored), and a write issued immediately after the previous one.
- Checks the decoded bytes (`0x42`, address, data), that `busy` rises right after `start` and falls after `done`, that `done` arrives about 285 µs after `busy` rises, and that the bus returns to idle-high.

### `sequencer` testbench

- A fake SCCB master raises `busy` after `start` and pulses `done` after a fixed delay, matching the real handshake. `WAIT_COUNT` is shortened for simulation.
- Phase 1: `cam_ready` low — no activity. Phase 2: full run — every entry arrives in order and matches the table, `start` is one cycle long and is never issued while busy, before `cam_ready` or after `config_done`, the gap after entry 0 equals the post-reset wait, later entries follow as soon as the previous write finishes, and `config_done` rises only after the last `done`. Phase 3: reset while finished — `config_done` clears and the sequence restarts from entry 0.

### Integration check

The sequencer was also simulated driving the real `sccbMaster`: every table entry appeared on SIOC/SIOD as the correct 3-byte write with all ACK slots released, the post-reset gap was visible between the first two writes, and `config_done` was still low when the final write completed.

### Stand-in PLLs

An ALTPLL instantiates Altera primitives that a simulator does not model. The testbenches that need one therefore define a stand-in module with the same name and ports (`cam_pll`, `pix_pll`) that produces a clock and raises `locked`, and the generated PLL files (kept under `ip/`) are left out of the simulation. The RTL is identical in simulation and synthesis. The remaining testbenches follow the same self-checking style and print `PASS` or `FAIL` with an error count.

### `clockAndResetControl` testbench

- A stand-in `cam_pll` with a testbench-controlled `locked`, and both waits shortened through parameters.
- Checks: outputs idle while the button is held and while the button is released but the PLL is unlocked; the order of events (PWDN falls, `cam_reset_n` rises `WAIT_CYCLES_AFTER_PWDN` + 1 cycles later, `cam_ready` rises `WAIT_CYCLES_AFTER_RESET` + 1 cycles after that); loss of lock after `cam_ready`; loss and return of lock in the middle of the long wait (the gap check shows the counter restarted from zero); a button press while ready and during the PWDN gap.
- The check limits are derived from the parameters, so the same testbench was also run once at the real values (1000 and 500,000 cycles).

### `enSynchronizer` testbench

- Reset active from time zero with `config_done` already high: `en_sync` is 0 after the first edge, never X.
- `en_sync` rises exactly two PCLK edges after `config_done` rises, and falls exactly two edges after it falls.
- A reset while `config_done` is still high clears `en_sync` on the next edge and holds it low; after release it returns two edges later.
- Metastability itself cannot be shown in simulation, so this proves the logic only.

### `resetSynchronizer` testbench

- Assert between clock edges: the output falls at once, before any edge.
- Release: the output rises exactly two clock edges later, and always right after a rising edge, never mid-cycle.
- A press that starts and ends between two clock edges is still caught.
- Clock stopped: the assert still works, and the release waits until the clock restarts.

### `vgaTimingGenerator` testbench

- Totals shrunk through the parameters so the run is fast; the checks use the specification numbers, not a copy of the module's comparisons.
- Checks: HSYNC width, VSYNC width in clocks, frame length, number of visible clocks per frame, maximum of both counters, outputs idle after a reset in the middle of a frame.

### `buffer` testbench

- Runs at the real size with two unrelated clocks (40 ns and 38 ns).
- Writes all 640×480 positions with a unique colour per position, followed after every valid pixel by one not-valid cycle with a garbage colour and the position numbers held, as the capture module does. A write that ignored `pixel_valid` would overwrite the data.
- Reads back every position with `x` and `y` changing on every clock, and checks that each stored pixel appears as a 4×4 block and that `rd_data` follows `x`, `y` by exactly one clock. A stray write, a wrong address or a wrong latency shows up as a mismatch.

### `outputTopModule` testbench

- A stand-in `pix_pll` with a testbench-controlled `locked`.
- The pixel side stays idle (counters 0, syncs high, colour black) while the button is held and while the button is released but the PLL is unlocked.
- The pixel reset releases exactly two `clk_pix` edges after the PLL locks.
- Over more than two frames, `colour` equals `rd_data` while `visible` is high and is black otherwise, and every frame has exactly 640×480 visible clocks.
- Loss of lock and a button press in the middle of a frame both return the pixel side to idle, and it restarts afterwards.

### `topModule` testbench (end to end)

- A camera stand-in: PCLK follows XCLK only while the camera is awake (reset high, power-down low), and it streams small 16×8 frames of a known pattern (VSYNC, HREF, RGB565 high byte first) from the moment it wakes, so the capture module's wait for the enable and for the first VSYNC is exercised. Both PLLs are stand-ins that lock by themselves.
- An SCCB monitor decodes the bus (start, 27 clock pulses, stop) and checks that nothing starts before `cam_ready` and that the first write is `0x42 0x12 0x80`, the soft reset. The long waits are shortened with `defparam`.
- Checks: no `pixel_valid` before the enable; every captured pixel equals what the camera sent for that position; at the VGA pins the top-left 16×8 region shows each stored pixel as a 4×4 block, aligned with `x` and `y` one clock earlier, and the colour is black outside the visible area.
- A button press in the middle of a run returns the camera to reset and the configuration to its start, and the whole path works again afterwards.

## 7. Development notes

Problems met during development and how each was resolved:

- **Edge detection without extra clocks.** An early attempt to reset counters on the edges of VSYNC and HREF gave multiple drivers on the same register. Resolved by keeping delayed copies of both signals and detecting edges inside the single PCLK block.
- **Counter and valid-flag alignment.** Updating `pixel_no` on the same edge as `pixel_valid` made the first pixel read 1. Resolved by incrementing from `pixel_valid`, and checking the end-of-line case so the reset takes priority.
- **FSM structure.** A two-register `next_state` style delayed every state by a step. Resolved by moving to a single clocked block with direct state assignments.
- **SCCB ordering and tri-state.** The protocol requires SIOD to move while SIOC is high at start and stop, which cannot be done with simultaneous non-blocking assignments. Resolved by giving each change its own tick, and by controlling SIOD through a separate output-enable.
- **Handshake lag.** Waiting for `busy` to fall can end early because `busy` rises one cycle after `start`. Resolved by waiting for the `done` pulse.
- **Reset coverage.** Missing reset values (X in simulation) and a guard that covered only one line of the reset branch were fixed, and the testbenches check that nothing is active during reset.
- **VGA counters and sync timing.** The vertical counter first advanced on every clock, and its wrap test sat outside the horizontal-wrap branch, which cut the last line short. Both counters were first sized from the visible size and not from the totals, which overflows `y`. Resolved by updating `y` and wrapping it only on the edge where `x` wraps, and by sizing from the totals. A "minus one" in the comparison, correct for `x` (which changes every clock), also moved VSYNC by a whole line, because `y` changes once per line; the vertical range was corrected to lines 490 and 491 and the horizontal one-clock offset was kept deliberately and documented.
- **Reset path.** The two lock-synchronizer flops in `clockAndResetControl` were first cleared from the branch that is active while the lock is low, so the lock could never reach the FSM and the camera was never released. Their reset now depends on `reset_n` only. In the reset synchronizer, the first flop's data input was first the raw reset, replaced by a constant 1. A separate 50 MHz lock synchronizer in the output top was removed, because `resetSynchronizer` already accepts an asynchronous input.
- **Buffer alignment.** Registering the write enable, the address and the index in separate stages made the enable, the address and the colour describe three different pixels, and the read path took three clocks against one for `visible`. Resolved by deriving the write enable and address combinationally from capture's registers, and by making the read address a wire so the RAM's register is the only stage. The read address first used the undivided `x` and `y`, and `pixel_valid` was missing from the write enable. The memory array was also first declared with word width and depth swapped.
- **Top-level wiring.** A misspelled port name in a positional instantiation silently created a new one-bit wire and left `xclk` undriven, and a reference to a deleted register left a reset input at X. Both compile; named port connections or `` `default_nettype none `` turn such mistakes into errors.

## 8. Known limitations and future work

- The SCCB master supports writes only.
- At the end of each ACK slot (state S6), SIOC falls and SIOD is driven again on the same clock edge. This is correct in simulation, but a one-tick guard band would add margin on real hardware.
- The SCCB master's stop marker relies on the last (placeholder) bit being 0, so SIOD is already low when SIOC rises.
- In the sequencer, S2 moves to S3 even if it did not issue `start` (only possible if `sccb_busy` were high there). Moving that transition inside the `if` makes this robust.
- The SCCB tick period (125 cycles) is a literal in the master. Making it a parameter would make the SCCB speed a one-line change.
- Pin locations and timing constraints are not yet assigned: the Timing Analyzer reports unmet requirements only because there is no constraints file. The three clocks (`clk_50MHz`, PCLK, `clk_pix`) must be declared asynchronous to each other, and PCLK must be on a clock-capable pin.
- The wait after the PWDN release (1000 cycles) is not taken from a datasheet minimum, and the 10 ms power-up wait is taken from the camera's start-up description; both are parameters and should be confirmed against the OV7670 power-up timing.
- The display is a 160×120 picture scaled 4×, so it is blocky, and the camera and display are not frame-synchronized, so tearing is possible.
- The buffer is correct only for a 640×480 camera output; another size changes the write rule (the low-bit test and the shifts).
- At the pins HSYNC is one clock ahead of the colour (front porch 15, back porch 49 clocks), and the pixel clock is 25.000 MHz instead of the nominal 25.175 MHz (about 59.5 Hz). Both are within what monitors accept.
- The colour stage is combinational. Registering it for cleaner pins would need one more flop on each sync output.
- `colour` is a 16-bit RGB565 bus (5, 6 and 5 bits); the width of the resistor ladders per channel must be confirmed, and if a ladder is narrower the top bits of each field are used.
- The PCLK reset synchronizer releases only while PCLK is running, so the capture side stays in reset until the camera drives PCLK.
- The testbenches use stand-in PLLs, so the real PLL's lock time is not simulated.
